Getting Started

Install the classes, register the template, and get a message out of a Clarion program in about twenty lines.

No DLL to shipNo .NET9 provider APIsClarion 10 – 12

What emailTo is

emailTo sends e-mail from a Clarion application, and manages the account it sends through. It is seven classes, one bundled C file and ten templates, and it deploys as part of your .EXE — there is no DLL to ship, no .NET, no OpenSSL and nothing to register on the machine it runs on.

It can put a message on the wire four ways, and they all send the same message: SMTP over plain, STARTTLS or implicit TLS; the Gmail API; Microsoft Graph; or a provider API key for SendGrid, Mailgun, Resend, Brevo, Postmark, Mailjet, SparkPost, MailerSend and Amazon SES.

Those nine API providers answer questions as well as taking messages, and the same account asks them: who is blocked and why, what the last month looked like, which contacts and campaigns exist. One set of methods covers all nine — see Who is blocked, and why.

You haveUseWhat you need
A Gmail accountSMTP + app passwordTwo-factor on, then an app password
Outlook.com or HotmailSMTP + OAuth2A desktop client ID from Azure
Microsoft 365 at workGraph, or SMTP + OAuth2A desktop client ID, and your tenant
A company mail serverSMTP + passwordHost, port, and whether it wants STARTTLS
None of the aboveAn API key serviceA free key from Resend or Brevo

Install

Or let the installer do it

emailToSetup.exe finds every Clarion 10 or later on the machine — from the IDE’s own settings and from a sweep of the fixed drives — copies the templates and the classes into the ones you tick, and registers each with that installation’s own ClarionCL. It leaves this manual, the dictionary and the demos on disk beside them. The rest of this page is exactly what it does, for anyone who would rather place the files themselves.

Clarion 10 gets a build of the template whose prompts are laid out for its narrower AppGen dialog — 480 px, against 960 from Clarion 11 on. Same template name, same generated code, so an application moves between them.

Copy these eleven files to a folder on the Clarion redirection path — the application folder, or \clarion12\accessory\libsrc\win:

FileWhat it is
EmailNetClass.inc / .clwSockets, TLS, HTTPS, DPAPI. Compiles the C in.
EmailMsgClass.inc / .clwThe message and its MIME. Pure Clarion.
EmailToClass.inc / .clwAccounts, the four transports, OAuth2, the windows.
EmailJsonClass.inc / .clwReading what a provider answers. Pure Clarion.
EmailApiClass.inc / .clwThe management API: blocked, statistics, campaigns.
emailc.cWinsock, SCHANNEL, WinHTTP, DPAPI, SHA-256.

And a dictionary, if you want the answers kept

emailToTables.dctx ships with them: seven tables — the blocked list, statistics, activity, contacts, lists, campaigns, and the account itself. Dictionary Editor → File → Import, and pick the DCTX / XML entry. You only need it if you add the emailTo - Sync extension; sending and the management window do not use it.

Not the .txd beside it — that is Report Writer’s format, and the Dictionary Editor says so in as many words.

Put emailTo.tpl in \clarion12\accessory\template\win and register it — in the IDE, or from a command line:

ClarionCL.exe -tr "C:\clarion12\accessory\template\win\emailTo.tpl"

The sources must be ANSI, with CRLF line endings

Clarion mis-parses an LF-only include: you get Illegal data type: EMAILTOCLASS reported at the declaration, with nothing flagged inside the include itself. If you have moved these files through a tool that rewrites line endings, convert them back before hunting for a phantom syntax error.

The smallest thing that sends

No template, no window, no dictionary. This is a complete program:

  PROGRAM

  INCLUDE('EmailToClass.INC'),ONCE

  MAP
  END

Mailer  EmailToClass

  CODE
  Mailer.Init(PATH() & '\mail.ini')          ! where the account is remembered

  Mailer.SetProvider(ETPrv:Gmail)             ! host, port, security, sign-in
  Mailer.Acc.UserName = 'you@gmail.com'
  Mailer.Acc.Password = 'abcd efgh ijkl mnop' ! a Google APP PASSWORD, not your own
  Mailer.Acc.FromAddr = 'you@gmail.com'
  Mailer.Acc.FromName = 'Acme Dispatch'

  IF Mailer.SendSimple('bob@example.com', 'It works', 'Sent from Clarion.')
    MESSAGE('Sent.')
  ELSE
    MESSAGE(CLIP(Mailer.LastErrorText))
  END

Two things are worth noticing. SetProvider fills in the host, the port, the security and the sign-in method for you, so the only lines left are the ones that are actually about your account. And nothing here checks a return code except the send itself — every failure ends up in LastErrorText as a sentence you can show a user.

Where the app password comes from

Google, Yahoo and iCloud will not accept your normal password from a program. Turn on two-factor authentication, then generate an app password — a sixteen-character string issued for one application. Paste that into Acc.Password. Outlook.com no longer offers this route at all: it is OAuth2 or nothing, which the Programmer's Guide covers.

Building it by hand

The class files pull themselves into the build through their LINK attribute, and EmailNetClass.clw pulls in the C through its PRAGMA, so a hand-coded project needs no file list. It does need the two link-mode defines that the template would otherwise write for you:

<Project DefaultTargets="Build" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup>
    <DefineConstants>_ABCDllMode_=&gt;0%3b_ABCLinkMode_=&gt;1%3b_emailToDllMode_=&gt;0%3b_emailToLinkMode_=&gt;1</DefineConstants>
  </PropertyGroup>
</Project>

Leaving the defines out does not fail to link

Without _emailToLinkMode_ the classes link as imports from a DLL that is not there, and the program takes an access violation inside a constructor before main() runs. The call stack shows nothing of yours on it, so it looks like anything except a project setting.

The same thing from AppGen

Two steps, and no code:

  1. Global Properties → Extensions → Insert → emailTo - Global. Fill in the Account tab: provider, from address, user name. That declares the object, sets the defaults and loads the stored account at start-up.
  2. Drag emailTo - E-mail button onto a window. Choose what it does — open the compose window, send a fixed message, or open the account setup window — and you are finished.

The account is set once, not per button

Step 1 is where the sender lives — server, from address, user name, password, OAuth2 client. Step 2 never asks for any of it. That division is the whole point: put five e-mail buttons on five windows and there is still exactly one account, in one place, for the whole application.

To let the user change it at run time, give them a button whose action is open the account setup window. What they save there overrides the Account tab.

From any embed anywhere else in the application, the object is simply there:

Mailer.SendSimple(Cus:Email, 'Your statement', 'Attached.', Loc:PdfName)

A message with more in it

SendSimple covers a note with one attachment. Anything richer is built on Mailer.Msg and handed to Send:

  Mailer.Msg.ClearAll()
  Mailer.Msg.AddTo('bob@example.com', 'Bob Smith')
  Mailer.Msg.AddCc('accounts@acme.com')
  Mailer.Msg.SetSubject('Invoice ' & CLIP(Inv:Number))
  Mailer.Msg.SetText('The invoice is attached.')
  Mailer.Msg.SetHtml('<p>The invoice is <b>attached</b>.</p>')
  Mailer.Msg.Attach('C:\invoices\INV-1042.pdf')

  IF NOT Mailer.Send(Mailer.Msg)
    Mailer.ShowError()
  END

You do not tell it what kind of MIME document to build. Text alone is text/plain; text and HTML together become multipart/alternative; an inline image makes it multipart/related; a file attachment wraps the lot in multipart/mixed. A plain note does not arrive as a four-part tree.

Setting up OAuth2, step by step

This is the part that stops people, and almost always for one of two reasons: the redirect URI does not match, or the application was registered as the wrong type. Both are fixed at the provider, not in your code.

Google

  1. Go to console.cloud.google.com and pick or create a project.
  2. APIs & Services → OAuth consent screen. Choose External, fill in the app name and your e-mail, and save. While it is in Testing, add your own address under Test users — a project in testing will refuse anybody who is not on that list.
  3. Add the scope you actually need: https://mail.google.com/ for SMTP, or https://www.googleapis.com/auth/gmail.send for the Gmail API.
  4. Credentials → Create credentials → OAuth client ID, and set Application type to Desktop app. Not Web application — a web client will not accept a loopback redirect.
  5. Copy the Client ID into the Sign-in tab. Google may also show a client secret; paste it if there is one, leave it blank if there is not. Neither is sensitive here, because the flow is PKCE.

You do not register a redirect URI for a Google desktop client

Desktop clients may use any loopback port, so there is nothing to type. emailTo sends http://127.0.0.1:<port>, which is the form Google documents.

Microsoft — Outlook.com and Microsoft 365

  1. Go to portal.azure.com → App registrations → New registration.
  2. For supported account types pick Accounts in any organizational directory and personal Microsoft accounts if you want both work and Outlook.com; that is the one that matches a Tenant of common.
  3. Under Redirect URI choose the platform Mobile and desktop applications and tick http://localhost. This is the step people miss — leave the platform as Web and the sign-in is refused with a redirect URI error.
  4. Authentication → Allow public client flows → Yes.
  5. API permissions → Add a permission → Microsoft Graph → Delegated. Add Mail.Send and offline_access for Graph, or SMTP.Send and offline_access for SMTP.
  6. Copy the Application (client) ID into the Sign-in tab. Leave the client secret blank — a public client that sends one is rejected.

Match the redirect host to what you registered

Because Azure offers http://localhost and Google documents http://127.0.0.1, emailTo sends whichever one suits the provider you picked. It listens on both loopbacks either way, so a browser that resolves localhost to ::1 — which is what Windows does first — still arrives. If you registered something different, say so:

Mailer.OAuth.RedirectHost = '127.0.0.1'

Google says “Access blocked”

“Access blocked: <your app> has not completed the Google verification process.” This is the consent screen refusing you, not emailTo failing, and it has two causes that produce almost the same wording. Which one you have is decided by your app’s publishing status.

Publishing statusWhat the block meansWhat to do
TestingThe account you are signing in with is not on the Test users list. The screen usually adds “currently being tested… developer-approved testers”.Google Auth Platform → Audience → Test users → Add users, and add the exact address you sign in with.
In production, unverified, with https://mail.google.com/That is a restricted scope. Unverified, Google blocks it outright — there is no Advanced link to click past.Either go back to Testing and use Test users, or switch to the gmail.send scope.
In production, unverified, with gmail.sendThat is a sensitive scope, so you get a warning rather than a block.Click Advanced → Go to <your app>. It is your own app; the warning is expected.

Publishing is not automatically the fix

Staying in Testing has its own cost: Google expires a refresh token after seven days, so a sign-in that worked stops working the following week. Publishing removes that — but only helps if your scope is gmail.send. Publish while asking for https://mail.google.com/ and you trade a weekly re-login for a permanent wall.

So if you are going to use OAuth on Gmail, use the Gmail API transport. emailTo then asks for gmail.send, which is the narrower scope and the one you can publish unverified.

For a single Gmail account, an app password avoids all of this

No consent screen, no verification, no seven-day expiry, and nothing to register. Turn on 2-Step Verification, generate an app password at myaccount.google.com/apppasswords, and use it as the SMTP password — with the spaces removed. OAuth earns its keep when you are shipping to other people’s mailboxes, or when a Workspace admin has turned app passwords off.

Running it

Set the account to use OAuth, then press Sign in… in the setup window — or call it yourself:

  Mailer.SetProvider(ETPrv:Office365)         ! or ETPrv:Gmail, or ETPrv:Outlook
  Mailer.Acc.Transport = ETTrn:GraphApi       ! or ETTrn:Smtp with AuthMode XOAUTH2
  Mailer.Acc.ClientId  = '11111111-2222-3333-4444-555555555555'
  Mailer.Acc.TenantId  = 'common'
  Mailer.Acc.UserName  = 'you@company.com'
  Mailer.Acc.FromAddr  = 'you@company.com'

  IF Mailer.Authorize()                       ! browser opens, user consents
    Mailer.SaveAccount()                      ! keeps the refresh token, sealed
    MESSAGE('Signed in.')
  ELSE
    MESSAGE(CLIP(Mailer.LastErrorText))
  END

Your browser opens at the provider. Sign in, agree to the permissions, and the page comes back saying you can close the tab. That is the whole of it: from then on the refresh token is stored and nobody sees a browser again.

When it fails, read the URL

The exact address that was opened is kept in Mailer.OAuth.LastAuthUrl, and it is written to the log. Paste it into a browser by hand and the provider will tell you precisely what it objects to — which beats guessing from a generic failure.

What the provider saysWhat to change
redirect_uri_mismatchGoogle: the client is a Web application, not a Desktop app. Microsoft: the platform is Web, not Mobile and desktop.
invalid_client / The OAuth client was not foundThe Client ID is wrong, or belongs to a different project or tenant.
unauthorized_clientMicrosoft: Allow public client flows is still No.
access_denied, and you are a test userGoogle: your address is not in Test users on the consent screen.
Sign-in works, the second send asks againNo refresh token was issued. Google needs the consent screen re-approved; emailTo already sends access_type=offline&prompt=consent.
The browser opens and nothing ever comes backSomething is holding the loopback port. Pin one with Mailer.OAuth.RedirectPort and allow it through the firewall.

Who is blocked, and why

Sending is half of what a mail provider does. The other half is keeping a list of the addresses it will not deliver to — the ones that hard bounced, the people who pressed "this is junk", the ones who unsubscribed. Left alone that list stays on their web site, and your program keeps mailing addresses that can never arrive, which is exactly what ruins a sending reputation.

EmailApiClass reads it. One object, borrowing the account you already set up:

  PROGRAM

  INCLUDE('EmailApiClass.INC'),ONCE

  MAP
  END

Mailer   EmailToClass
MailApi  EmailApiClass
i        LONG

  CODE
  Mailer.Init(PATH() & '\mail.ini')
  Mailer.LoadAccount()                        ! the key you stored in Setup
  MailApi.Init(Mailer)                        ! borrows that account - no second copy

  IF MailApi.GetSuppressions(ETSup:All) < 0
    MESSAGE(CLIP(MailApi.LastErrorText))
  ELSE
    LOOP i = 1 TO RECORDS(MailApi.SuppQ)
      GET(MailApi.SuppQ, i)
      !  MailApi.SuppQ.Address   who
      !  MailApi.SuppQ.KindName  bounce / blocked / spam report / unsubscribed
      !  MailApi.SuppQ.Reason    what the receiving server actually said
      !  MailApi.SuppQ.WhenDate  when
    END
  END

That program works unchanged against all nine API providers. It has to, because they agree about almost nothing:

ProviderWhere the blocked addresses areWhat a row looks like
SendGridFive separate lists: bounces, blocks, spam_reports, unsubscribes, invalid_emailsemail, reason, a unix created
BrevoOne list, /smtp/blockedContacts, with a reason CODE saying which kind it isemail, reason.message, an ISO blockedAt
MailgunPer DOMAIN, and paged with a cursor rather than an offsetaddress, error, code, an RFC-2822 date
PostmarkA stream dump, plus a richer /bounces for bounces aloneEmailAddress, SuppressionReason — capitalised
MailjetEverything wrapped in Data, capitalised throughoutContactAlt, ErrorRelatedTo, ErrorCode
Amazon SESSigned with SigV4 rather than a key in a header, and paged with a continuation tokenEmailAddress, Reason — BOUNCE or COMPLAINT

After GetSuppressions() they are one queue with the same columns, and SuppQ.Kind says which sort of block each row really is — worked out from the provider's own wording where the provider keeps them all in one list.

Ask before you send

IsBlocked() searches whatever the last GetSuppressions() loaded. Calling it in the loop that builds a mailing costs nothing and stops you sending to an address the provider is going to refuse anyway:

IF MailApi.IsBlocked(CUS:EMail) THEN CYCLE.

The rest of the account

The same object answers the other questions, and every one of them fills a queue of the same shape whoever the provider is:

You wantCallIt fills
Who is blockedGetSuppressions(kind)SuppQ
Let one back inDeleteSuppression(address, kind)—
Let them all back inDeleteAllSuppressions(kind)—
Statistics per dayGetStats(from, to)StatQ
What happened to a messageGetEvents(from, to)EventQ
Contacts and listsGetContacts() GetLists()ContactQ ListQ
CampaignsGetCampaigns() SendCampaign(id)CampaignQ
Templates, senders, domains, webhooksGetTemplates() …TemplateQ …
All of it, in a windowManage()—

No provider offers every one. Supports() says which, so a window can grey out what this account genuinely cannot do rather than failing when somebody presses it:

  IF NOT MailApi.Supports(ETOp:Campaigns)
    DISABLE(?Campaigns)                       ! Mailgun has no campaign API at all
  END
  IF NOT MailApi.Supports(ETOp:Suppressions)
    DISABLE(?Blocked)                         ! Resend keeps no block list
  END

Or just show them the window

MailApi.Manage() is a complete tabbed window over all of it — blocked addresses with their reasons, unblock one or unblock every one, a CSV export, statistics, activity, contacts, lists, campaigns, templates, senders, domains and webhooks. Tabs this provider cannot answer are disabled rather than empty. The emailTo - Mail account button control template drops a button that opens it, on whichever tab you name.

The demo

examples/emailTo/emailToDemo.clw is the hand-coded equivalent of what the templates generate: a window with Account setup, Write a message and Send a test, and the conversation log underneath. Build it and press the buttons before wiring anything into your own application.

MSBuild emailToDemo.cwproj -t:Build -p:Configuration=Debug -p:Platform=Win32
emailToDemo.exe            ! the demo window
emailToDemo.exe /setup     ! straight to the account window

Test account is the button to press first. It connects, negotiates TLS and authenticates, then hangs up — it sends nothing to anybody, so you can prove the credentials without mailing a real person.

When the first send does not work

Turn the log on (Mailer.Trace = 1) and read the Log tab of the setup window. Every line the server said is there, with passwords masked. These are the answers that come up first:

What you seeWhat it means
The password was refused on GmailA normal password, not an app password. Or two-factor is off, so Google will not issue one.
The password was refused on Outlook.comMicrosoft turned basic authentication off for personal accounts. Use OAuth2.
The TLS handshake failed, Windows code 590624That is SEC_I_INCOMPLETE_CREDENTIALS. emailTo already handles it; if you see it, you are running an older copy of emailc.c.
Could not connect to the mail serverA firewall, or the wrong port. 587 is STARTTLS, 465 is implicit TLS, 25 is plain.
The sender was refusedThe From address is not one the account is allowed to send as.
Illegal data type: EMAILTOCLASS at compile timeThe includes arrived with LF line endings. Convert them to CRLF.
