SDAspecto

One look for every window in the application — typography, colours and a CSS-like rule engine — from a single global extension. No per-window work, no per-control work, and nothing to undo when you change your mind.

ABC · 1 app extension + 2 procedure extensions · rules live in an INI · multi-DLL · thread-safe

Overview #

SDAspecto walks the controls of every window as it opens and restyles them from a set of rules held in memory. It is the successor to SdTpl.TPL and BSTheme.

It does four separate jobs, and they are worth keeping apart in your head because they are configured separately and fail separately:

JobWhat it doesConditional?
TypographyOne typeface, size, colour, style and charset for the whole programNo — applied to everything in scope
RescalingPuts the controls back where they belong after the font changed their sizeNo
Fixed settingsA minimum control height, and a background colour per control typeNo
RulesBackground, font colour/style, flat buttons, tips and cursorsYes — matched per control

The first three are applied always and identically. The rules run after them, so a rule can override a fixed setting on one particular control without you having to carve an exception into the fixed setting itself.

Language The prompt UI, the INI keys and the source comments of this template are in Spanish, as written. This document is in English.

Install & register #

SDAspecto.inc    → libsrc\win — the class: rule queue, per-window state, prototypes
SDAspecto.clw    → libsrc\win — the engine: matching, painting, rescaling, the INI
SDAspecto.tpl    → template\win — the chain file
SDAspecto.tpw    → template\win — the extensions
  1. Copy the four files as above.
  2. Setup → Template Registry → Add → SDAspecto.tpl.
  3. In the Application Tree: Global → Extensions → Add → SDAspecto - Personalizacion visual de controles.
The .tpw is not optional SDAspecto.tpl is a chain file whose only job is #INCLUDE('SDAspecto.tpw'). If you copy the .tpl and leave the .tpw behind, registration fails on a file it cannot find.

Quick start #

Add the global extension, set a typeface on the Tipografia tab, generate and build. That alone restyles the whole application. Everything else is refinement.

The scheme name and the global instance name are the only two required prompts. The instance defaults to GLO_SDAspecto, which is the name you use from your own code:

GLO_SDAspecto.FuenteNombre = 'Segoe UI'
SDAspectoApply()                     ! repaint the current window
Multi-DLL: the instance name must be identical everywhere It is one variable for the whole system. The app that owns the globals declares and exports it; every other app declares that same name as EXTERNAL and imports it. If the name differs in one app, the linker asks for a symbol nobody defined.

The four prompt tabs #

General

Scheme name, global instance name, a switch that disables the whole template (%SDADisable — every #AT carries WHERE(%SDADisable=0), so nothing is generated at all), and a diagnostic mode that pops a message per window listing the rules loaded, the buttons found, the text they were compared against, and which rule matched each one. Turn it off in production.

Tipografia

Typeface, size, font colour, style and charset. Every parameter is either a literal or a program variable — a tick chooses which — so a global theme variable can drive it. Scope selects the window, its controls, or both.

−1 and empty mean “leave this one alone” That is the convention throughout: a size of -1 or an empty typeface name is not a value, it is an instruction to skip that parameter. It is what lets you change only the size and inherit the rest.

This tab also carries rescaling and recentring — see Rescaling, which is where the interesting part is.

Only one template may own the fonts If something else in the application already reapplies fonts or rescales windows, turn this off. Two engines rescaling the same window fight each other, and the winner depends on embed priority rather than on intent.

INI

Where the settings and the rules are read from. The path is relative to the executable if it starts with .\.

The template is the factory default; the INI is the customisation The INI is read after everything configured in the template, so it overrides it. If the file does not exist, or does not carry some key, what the template said stands. This matters more than it sounds: reading a prompt at generate time tells you the factory value, not what the program will actually apply.

Fijos

Settings that are applied always and unconditionally, like the typography — not rules. A minimum height for ENTRY, SPIN, CHECK, COMBO, LIST and BUTTON; and a background colour per control type, each behind its own tick so that unticked means do not touch that type.

GROUP is deliberately absent A GROUP is not a fillable surface. To colour the area of a group, put a PANEL or a REGION behind it.

TAB colouring requires the visual style to be switched off in the application manifest; with it on, Windows draws the tab itself and ignores the colour.

Windows that need an exception #

Two procedure extensions, added to individual procedures.

SDAspecto - Excluir esta ventana

Leaves one window completely alone — no colours, no typography, no rescaling, no minimum height. It generates no code of its own: its mere presence makes the global extension emit nothing into that procedure's embeds, so the window is untouched rather than touched and then reverted. Nothing to configure.

SDAspecto - Ventana redimensionable o maximizada

Needed when a window uses the ABC resizer, or has to start maximised. It is a per-procedure extension rather than a global option on purpose: the resizer belongs to the window, not to the application, and a global switch would force all-or-nothing — and in procedures without a resizer the compiler would object to an object that does not exist.

The problem is ordering. Three things happen in Init, in this order:

PriorityWhat happens
8125Resizer.Init takes its baseline: it walks the controls and stores each one's position and size.
8600SDAspecto rescales for typography and moves all of them.
deferredSDAspecto's second pass, with the window fully built.

So the resizer photographs the layout before the rescale and is left with a baseline that does not correspond to anything. It is worse if the window maximises during Init: the resizer stores the maximised size alongside the design-time positions, concludes that this small layout is what a full screen looks like, and never spreads anything out again. This extension puts the two back in order at the end of the deferred pass.

What a rule is #

A rule is match criteria + actions.

CriteriaMatches on
TypesA list of control types (ENTRY,SPIN,TEXT,LIST,COMBO,…)
TextA list of strings, compared exact, contains or starts-with
PictureA wildcard over PROP:Text — so “every currency field” is expressible
Required / read-only / disabledThe control's state
ActionsSets
sdAct:ColorBackground colour
sdAct:FontColorFont colour — or sdColor:Auto
sdAct:FontStyleFont style
sdAct:FlatFlattens a button
sdAct:TipTooltip
sdAct:CursorMouse cursor

Criteria are restricted to properties the actions do not modify. That is what keeps the engine from matching on something it just changed.

sdColor:Auto Font colour accepts sdColor:Auto, which derives black or white from the luminance of the background — so a rule can set a background without also having to work out whether the text will still be readable on it. Its value (7FFFFFFFh) is chosen to dodge both real colours (00BBGGRRh) and system colours (80000000h–8000001Eh).

The cascade #

Rules are evaluated in order. Every rule that matches applies, and the last one wins per property — exactly like CSS. A broad rule sets the ground, a narrow one overrides a single property of it, and the narrow rule does not have to restate everything the broad one said.

A rule marked Cortar stops the cascade for that control. That is ELSIF semantics, available when you want it and out of the way when you do not.

The factory scheme is six rules: required fields, read-only fields, normal fields, the confirm button, the cancel button, and browse buttons.

Two bitmasks, and why #

Both of these look like over-engineering until the alternative is tried.

The actions are a bitmask

Because COLOR:NONE is -1, which is a valid colour and therefore useless as a “not set” sentinel. There is no value a colour field can hold that means “this rule does not set the colour”, so a separate bitmask declares which fields of the rule are defined.

“Required” is a bitmask too

ValueMeans
sdReq:AtributoREQThe control carries the REQ attribute
sdReq:FondoDisenioThe control was given a background colour in the designer
sdReq:AmbosEither of the two

REQ is the clean answer. But plenty of applications never used it and instead marked required fields by colouring them at design time — that is what SdTpl.TPL relied on. Supporting only REQ would mean those applications get nothing, and supporting only the colour would mean the tidy ones do.

The INI format #

Rules are data, not code. They live in the INI, one [Regla:n] section each, with a count in the main section:

[SDAspecto]
Esquema=SDigitales
FuenteNombre=Roboto Medium
FuenteTamano=9
Reglas=13                ! how many [Regla:n] sections follow

[Regla:1]
! ... one section per rule, with every field of it

The factory scheme is built in code and written out the first time, when the INI brings no rules. After that the INI is the source of truth, which means a scheme can be changed, shipped or rolled back without rebuilding anything.

When it runs #

EmbedPriorityWhat goes in
WindowManager.Init8600SDAspectoApply() + POST(SDAspecto:EventoRefresh)
WindowManager.TakeEvent990SDAspectoTakeEvent() — the deferred pass
WindowManager.Kill8600SDAspectoReset()

8600 is deliberately late in Init, so that any other template which reapplies fonts or moves controls has already finished.

Why there is a second pass at all Late in Init is still not late enough. ABC has code left to run after it — restoring the window position from the INI, initialising resizers — and that code can overwrite the geometry that was just set. This is why the first open used to look wrong and the second one right. The posted event is processed once the window has finished building itself, and the second pass fixes what moved. PRIORITY(990) is the same slot stabbwcs.tpw uses for this embed.

The scheme is loaded once at program start-up (%ProgramSetup, PRIORITY(1000)). Windows afterwards only walk their controls against the queue already in memory — there is no file access per window.

Rescaling #

Changing the font changes how big everything is, so every control ends up the wrong size. The engine puts them back, and the method is the whole trick:

  1. Save each control's geometry in dialog units.
  2. Apply the font with SETFONT.
  3. Force Clarion to recompute the dialog unit.
  4. Write the same numbers back.

The values did not change; what a dialog unit is worth did. Because every control starts from its original geometry and never from its current one, applying the font twice gives the same result as applying it once — the operation is idempotent instead of cumulative, which is what makes a live settings window safe.

LIST and COMBO line height and column widths come along too. Those are read as indexed properties (PROPLIST:width, PROPLIST:group), so no PROP:Format string ever has to be parsed or rebuilt.

Recentring

A window that grows keeps its top-left corner fixed, so it drifts down and to the right. With recentring on it is moved back by half of what it grew, and the centre stays where it was.

Threads #

The class instance is global and shared across every thread, and Clarion does not protect a shared QUEUE. So:

  • the rule queue carries a lock;
  • the per-window state queue is declared ,THREAD.
Per-window state is not class properties The current window's geometry and typography used to live as properties of the class, and that was wrong: the instance is unique and global, so two windows opening on different threads overwrote each other's state. They are a ,THREAD instance of a TYPEd group instead.

Multi-DLL #

The skeleton is the one cleansdw.tpw uses. MEMBER modules never see the SDAspectoClass type at all — they only ever call the five global functions.

App that owns the globalsSatellite DLLs
The INCLUDEIn both — it brings the equates and the type, and a ,TYPE generates nothing by itself
The instanceDeclared and exportedNot declared — only the functions are imported
Why the satellites do not declare it Declaring it EXTERNAL,DLL there would make the linker ask for every method of the class to be exported one by one. Calling five plain functions makes that problem not exist. Likewise the export list carries the five functions and the instance, but not the class: Clarion already exports the TYPE$, the VMT$ and the methods of a global instance, and doing it by hand produces Duplicate export name on all 46 symbols.

Run-time API #

Five global functions, visible from every module including MEMBER ones:

FunctionDoes
SDAspectoApply()Applies everything to the current window
SDAspectoReset()Undoes it for the current window
SDAspectoTakeEvent()The deferred pass; called from the generated embed
SDAspectoCargar()Rereads the INI — BYTE,PROC
SDAspectoGuardar()Writes the current state to the INI — BYTE,PROC

Parameters are edited straight on the global instance. A settings window is therefore just:

GLO_SDAspecto.FuenteNombre = 'Segoe UI'
GLO_SDAspecto.FuenteTamano = 10
SDAspectoGuardar()                   ! persist
SDAspectoApply()                     ! and show it now

VentanaConfigAspecto.txa in the template folder is a ready-made settings window; import it with Application → Import.

Reading the settings from another template Ask the instance, not the prompts. GLO_SDAspecto.FuenteNombre and .FuenteTamano are what the program is actually applying; the template prompts are only the factory default, and the INI overrides them at start-up. Honour FuenteActiva, honour FuenteAControles if what you are styling is a control, and treat empty / -1 as “leave it alone”. BrowseGrid integrates exactly this way.

Troubleshooting #

SymptomCause
Registration fails on a missing fileThe .tpw was not copied next to the .tpl.
The linker asks for a symbol nobody definesThe global instance name differs between apps in a multi-DLL system. It has to be identical everywhere.
A resizable window never spreads its controlsAdd SDAspecto - Ventana redimensionable o maximizada to that procedure. The resizer took its baseline before the rescale.
A TAB ignores its colourVisual styles are on in the application manifest; Windows is drawing the tab itself.
Controls drift further every time the font is appliedSomething else is rescaling the same window. Only one engine may own the geometry.
A settings change does not show upThe INI is read at start-up. Call SDAspectoCargar() then SDAspectoApply().
One window must not be touchedAdd SDAspecto - Excluir esta ventana to it.
Nothing matches what you expectedTurn on diagnostic mode: it reports the rules loaded, the controls found, the text compared and which rule matched each one.
